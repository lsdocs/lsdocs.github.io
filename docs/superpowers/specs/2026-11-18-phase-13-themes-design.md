# Phase 13, part 3: the flagship HTML theme

## Intent

Give lsdocs one polished, recognizable look: a theme of our own, visually
in the spirit of zensical-ui (header bar, navigation menus, a table of
contents sidebar, admonitions, a color palette with light and dark
schemes), built from scratch in plain modern CSS and framework-free
JavaScript, so it is ours to maintain and to diverge with. Compatibility
with other ecosystems' themes (Sphinx's Alabaster, MkDocs' default theme,
Zensical) comes later, as separate renderers on a shared core.

## Decided (with the user)

- **The flagship first.** Compatibility renderers later: Sphinx
  (Alabaster first; may become its own repository), MkDocs (its default
  theme; Zensical's templates use MkDocs' context, so a Zensical
  renderer only if it diverges). Furo, themes that run Python, PDF and
  LaTeX wait.
- **Three layers**, so themes are cheap and behavior is shared:
  1. **A content markup contract**: render-html writes page bodies with
     lsdocs' own semantic classes and data attributes.
  2. **One JavaScript component library**: custom elements (lifecycle
     from the browser), `AbortSignal` for listeners and requests, and
     `@preact/signals-core` for shared state (color scheme, search query,
     dismissed banners, the consent and feedback toggles). It binds to
     tags and data attributes, never to a theme's classes.
  3. **Themes**: templates plus CSS against the contract.
- **Plain modern CSS**: custom properties, nesting, cascade layers; no
  framework, no Sass, no CSS build step.
- **First features**: search, dark mode, code copy, content tabs, toc
  highlighting. Instant navigation later.
- **Not a zensical-ui fork**: zensical-ui is the visual reference (MIT;
  its RxJS-based TypeScript, Sass and minified, unreleased search engine
  are not taken). Anything copied keeps its license notice.

## Design

### 1. Content markup contract (render-html)

A documented set of classes and attributes for every node kind the body
writer emits, prefixed `lsd-`: `lsd-admonition` with `data-kind`
(`note`, `warning`, ...) and an `lsd-admonition-title`; `lsd-code` blocks
(`data-language`, line numbers and highlighted lines as data, a caption),
`lsd-tabs` / `lsd-tab`, `lsd-api-item` (signatures), `lsd-toc`, footnotes,
tables, definition lists, heading anchors. Written down in
`docs/content/reference/` as the theme authors' reference, and covered
by snapshot tests (the sample site). The current markup changes where it
must; snapshots are re-recorded and reviewed.

### 2. Shared content stylesheet

`content.css`: styles for the contract only (prose, code, admonitions,
tabs, tables, API items), driven by custom properties (`--lsd-fg`,
`--lsd-bg`, `--lsd-primary`, `--lsd-accent`, `--lsd-font-text`,
`--lsd-font-code`, spacing, radius), with light and dark values. Every
theme includes it and restyles by setting the properties; a theme may
replace it.

### 3. JavaScript components

Written in TypeScript (for readability), compiled with `tsc` alone to
plain ES modules (no bundler), loaded with `<script type="module">`. The
compiled output is checked in, regenerated by a `nur gen theme` task
(like the Node bindings' `native.js`), so building or using lsdocs needs
no Node; only working on the theme does. The signals library is vendored
as one ESM file with its license.
Elements: `<lsd-search>` (dialog, keyboard shortcut, results),
`<lsd-palette>` (light / dark / system; remembered in `localStorage`,
applied before first paint by a tiny inline script to avoid a flash),
`<lsd-copy>` (wraps code blocks), `<lsd-tabs>` (linked tabs: choosing a
label switches every tab set with it), `<lsd-toc>` (highlights the
current section with `IntersectionObserver`). Shared state in one
`state.js` of signals. Banners and the consent/feedback toggles are
state only for now (persisted in `localStorage`, no cookies; no analytics
script loads without consent), with elements added when a theme needs
them.

### 4. Search

Ours: render-html's `render/transform/all` writes a search index
(`search.json`: pages and sections with titles, anchors and text,
tokenized and lower-cased) and the `<lsd-search>` element queries it in a
Web Worker (prefix matching, ranking titles above text, highlighted
excerpts). Size and speed are measured on the docs site (my call: a
simple inverted index first; a real engine later if needed).

### 5. Themes

- A theme is a directory: `templates/` (minijinja, with `extends` and
  blocks: `base.html`, `page.html`, partials for header, nav, toc,
  footer, search), `assets/` (CSS, JS, images, copied to the output), and
  `theme.toml` declaring its settings and their defaults.
- **The flagship is built in** (embedded in render-html), named
  `default`, and is the default. Today's simple template stays as
  `plain` (my call), its page toc becoming a drop-down menu (as GitHub's
  file view has it) rather than a list in the content.
- **Choosing and configuring a theme**: render-html's settings
  (`.config/lsdocs/<name>/settings.toml`): `theme = "default"` (a built-in
  name or a directory), `[theme]` for its settings (validated against
  `theme.toml`), `overrides = "theme-overrides"` (a directory whose
  templates and assets replace the theme's, block by block). `site.theme`
  in `lsdocs.toml` is dropped (my call: one place for theme settings).
- **The flagship's settings**: palette (`scheme = "auto" | "light" |
  "dark"`, `primary`, `accent`), fonts (text, code; system fonts by
  default, no external requests unless set), logo and favicon,
  `language` with translatable labels (English first), extra CSS and JS,
  social links, footer text, edit-this-page links (a repository URL and
  path template).

### 6. Data for templates

- The navigation already comes from transform-nav (`page.nav`).
- The table of contents as data: transform-toc also writes the page's
  sections to metadata (`page.toc`), so a theme renders it in a sidebar
  instead of (or besides) inline (my call: transform-toc gets an
  `inline = false` setting; the flagship uses the sidebar).
- `page` (title, source, url, metadata, previous / next), `site`
  (title, base URL), `theme` (its settings), `lsdocs` (version), and the
  `link` filter as today.

### 7. Assets

render-html copies the theme's assets to `<output>/_lsdocs/` with a
content hash in each file name (cache busting), rewriting references;
the built-in theme's assets are embedded in the binary. No minification
step at first (the files are small); later if measured worthwhile.

## Goals

- The docs site builds with the `default` theme, configured only by
  settings (and at most a template override), without warnings, and
  looks like a modern documentation site at desktop and phone widths, in
  light and dark.
- The five first features work, keyboard-accessible, with no JavaScript
  framework and no build step for users.

## Non-goals

- Instant navigation; the Sphinx, MkDocs and Zensical renderers; PDF and
  LaTeX; versioning, blog, RSS; analytics integrations beyond the consent
  state; icons beyond a small set the theme uses.

## Anti-goals

- A framework or a compile step (Sass, a bundler) required to use or
  override the theme (the TypeScript is compiled ahead, its output
  checked in).
- Requests to third parties by default (fonts, CDNs, analytics).
- Markup that only one theme can style: the contract is the boundary.

## Approaches

- **Our own theme on a content contract, plain CSS, custom elements**
  (chosen).
- **Fork zensical-ui and diverge** (considered first): keeps its look and
  CSS work, but brings RxJS, Sass, MkDocs-shaped templates and pymdownx
  markup, and its search is not open source; since we would rewrite the
  TypeScript anyway, starting clean costs little more and avoids
  tracking an upstream we diverge from.
- **Themes built on CSS frameworks** (Tailwind, Bootstrap, Bulma):
  bundles without a compiler, but none styles documentation content, so
  each theme would redo it; dropped for plain CSS.

## Left to the builder

- The exact class list of the contract, within the `lsd-` scheme above.
- Template block names and partial boundaries.
- The search index's exact format and ranking details.
- Visual details (spacing, type scale, breakpoints), with zensical-ui as
  the reference look.
